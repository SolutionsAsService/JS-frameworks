Concepts

How they work

Three questions every framework answers differently: where the HTML is made, how a change is found, and how much is in the box.

Where the HTML is made

Before the first change, there is a first page. A framework decides who writes its HTML and when.

ModelWhat happensFrameworks hereThe trade
Client renderingThe server sends an almost empty page and a script. The browser runs the script, which draws everything.React, Preact, Vue, Svelte, Solid, Lit, AngularThe simplest to host. Nothing appears until the script has run, and search engines and slow phones feel that.
Server renderingThe server runs the components for each request and sends finished HTML. A script then hydrates it: it runs the components again in the browser to attach the event handlers.Next.js, Nuxt, Angular, Qwik, Svelte, SolidText shows at once. The page is paid for twice: rendered on the server, then run again in the browser.
Static generationThe HTML is made once, at build time, and served as files.Next.js, Nuxt, Astro, SvelteFast and cheap to serve; the page is only as fresh as the last build.
IslandsMost of the page is plain HTML. Only components marked as interactive get JavaScript, each hydrating on its own.AstroContent pages ship little script. Interactive pages need other tools.
ResumabilityThe server writes the application’s state and its event listeners into the HTML. The browser continues from there and loads code only when an event needs it.QwikNo start-up re-run. The first interaction may wait on a request for its code.
HypermediaThe server keeps the state and returns HTML fragments. The browser swaps them into the page.htmxNo client application to build. Every change that matters goes to the server.
Hydration, in a line: the server’s HTML is only text and boxes until a script runs the components again in the browser and wires them to it. Resumability and islands are two answers to the cost of that second run.

How a change reaches the screen

You change a number. Something has to find which part of the page showed that number and change it. There are six ways here, and many frameworks use more than one.

Compare two trees

Run the component again, get a new description of the UI, compare it with the old one, change the nodes that differ. Used by React, Preact, Vue.

  1. Component runs again
  2. New tree compared with the old
  3. List of differences
  4. DOM nodes patched

Vue also records what each component read, so it re-runs fewer components than React does.

Track what was read

State is a reactive value. Whatever reads it is remembered, and only that is run again when it changes. Used by Vue, Solid, Angular, Svelte, Preact.

  1. Value changes
  2. Readers of that value are known
  3. Only those run again
  4. The matching DOM updates

Solid tracks single expressions; Vue, a whole component render; Angular’s signals, a template binding; Svelte 5’s runes, the compiled update; Preact’s signals, the parts of a component that read them.

Compile it away

A compiler reads the component at build time and writes the exact update code, so little general-purpose framework code ships. Used by Svelte, Solid.

  1. Build reads the component
  2. It writes direct DOM updates
  3. Small runtime ships
  4. A change runs the generated update

The saving is smaller output; the cost is a compiler step and rules to learn.

Re-evaluate the template

A template is a function of the data. Run it again, but update only the parts of the DOM whose values changed. Used by Lit.

  1. A property changes
  2. Template runs again
  3. Only changed values compared
  4. Those DOM parts updated

No virtual DOM tree, a small library, and the browser’s own component standard.

Check the tree

After an event, the framework walks the component tree to see what changed. Angular’s traditional way, triggered by zone.js, which notices asynchronous events. Used by Angular.

  1. An event or response happens
  2. zone.js tells Angular
  3. Bindings are checked top-down
  4. Changed bindings update

Signals let Angular skip the walk, and it is moving toward them.

Ask the server

The state is on the server. The browser sends an event, receives HTML, and puts it in place. Used by htmx.

  1. An event fires
  2. Request to the server
  3. HTML fragment returned
  4. Fragment swapped in

It does not need client state, and it does need a round trip.

How much is in the box

The word framework covers three different sizes of thing.

SizeWhat it gives youHere
Rendering libraryComponents and a way to update the screen. Routing, data and building are yours to choose.React, Preact, Solid, Lit
Application frameworkThe view layer plus routing, forms, a way to talk to servers and a command-line tool, designed together.Angular, Vue. Vue’s router and store are official add-ons.
Meta-frameworkBuilt on a rendering library: file-based routing, server rendering, bundling and deployment.Next.js, Nuxt. Also SvelteKit on Svelte, SolidStart on Solid and Qwik City on Qwik.
Something elseAstro builds content sites and hosts other frameworks’ components; htmx adds behaviour to HTML with no components at all.Astro, htmx
