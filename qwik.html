resumable framework

Qwik

Do not run the app again in the browser: resume where the server stopped.

  • Kindresumable framework
  • Made byMiško Hevery, at Builder.io
  • Since2023 (1.0)
  • Written inTypeScript or JavaScript, with JSX
  • Checked on npm1.0.0 on 2023-05-02

At a glance

Pros

Built so that start-up cost need not grow with the app (not shown by a counter, which is too small). Code for a feature loads when used.

Cons

Developers must learn the $ rules about what can be serialised. A small ecosystem and few libraries built for it.

What it is

Qwik is built around resumability. Other server-rendering frameworks send HTML and then re-run the application in the browser to attach listeners and rebuild state. Qwik serialises that information into the HTML on the server, so the browser can continue from there without re-running anything.

Qwik City is its application framework, with file-based routing and server data loaders.

How it works

  1. Write components in JSX with $ boundaries
  2. The optimizer splits code at each $ into lazy chunks
  3. The server sends HTML with state and listeners serialised into it
  4. A tiny loader fetches only the code an interaction needs

Any function the author marks with a $ suffix, such as onClick$, becomes a boundary that the build can move into its own file. The page loads a very small script, the Qwikloader, which listens for events; when one fires it downloads just the code for that handler.

So the JavaScript that loads with the page is nearly constant however large the app is, and the JavaScript for a feature arrives when the user reaches for it. The cost shows after the first click, which is why this site measures both.

Overlaps and differences

Overlaps with

  • Solid: JSX with signals.
  • Next.js: Both render on the server and send HTML first.

Differs from

  • Next.js: Next.js hydrates, re-running client components in the browser; Qwik resumes without that step.
  • Angular: Its author’s earlier project: Angular ships a framework up front, Qwik delays everything it can.

What it is good at, and what it costs

Good at

  • Built so that start-up cost need not grow with the app (not shown by a counter, which is too small)
  • Code for a feature loads when used
  • Familiar JSX and signals

Costs

  • Developers must learn the $ rules about what can be serialised
  • A small ecosystem and few libraries built for it
  • First interactions can wait on a network request for their code
